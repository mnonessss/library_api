## Задание 4. Исследование SELECT без дополнительного индекса

Запрос:

```sql
EXPLAIN ANALYZE
SELECT * FROM lab02.events WHERE user_id = 123;
```

`user_id` равномерно распределён по диапазону 0…100 000, поэтому доля строк с `user_id = 123` всегда около 0.001%. На малых объёмах таких строк может не быть вообще — это видно на 10k и 100k.

| Количество строк | Scan | Actual Rows | Rows Removed by Filter | Execution Time |
| ---: | :--- | ---: | ---: | ---: |
| 10 000 | Seq Scan | 0 | 10 000 | 0.306 ms |
| 100 000 | Seq Scan | 0 | 100 000 | 3.557 ms |
| 1 000 000 | Parallel Seq Scan + Gather | 12 | 333 329 на воркера (×3 ≈ 1 000 000) | 16.980 ms |
| 5 000 000 | Parallel Seq Scan + Gather | 42 | 1 666 653 на воркера (×3 ≈ 5 000 000) | 72.421 ms |
| 10 000 000 | Parallel Seq Scan + Gather | 92 | 3 333 303 на воркера (×3 ≈ 10 000 000) | 136.747 ms |

План на 5 млн строк:

```
Gather  (cost=1000.00..68713.58 rows=50 width=36) (actual time=4.622..72.396 rows=42 loops=1)
  Workers Planned: 2
  Workers Launched: 2
  ->  Parallel Seq Scan on events
        Filter: (user_id = 123)
        Rows Removed by Filter: 1666653
Execution Time: 72.421 ms
```

### Вопрос. Как изменилось время выполнения запроса при увеличении объёма таблицы?

Время Seq Scan растёт линейно с числом строк: 0.3 ms → 3.6 ms → 17 ms → 72 ms → 137 ms. С 1 млн PostgreSQL включает параллельное сканирование (2 воркера), но это только смягчает константу, а не меняет сложность: по-прежнему читается вся таблица. `Rows Removed by Filter` почти совпадает с размером таблицы — индекс отсутствует, и условие проверяется на каждой строке.

**Вывод.** Без индекса точечный поиск по `user_id` деградирует пропорционально объёму данных. На маленькой таблице это незаметно, на миллионах строк — уже десятки и сотни миллисекунд на один простой `WHERE`.

## Задание 5. Добавление индекса

```sql
CREATE INDEX idx_events_user_id ON lab02.events(user_id);
```

На контрольных точках 100k / 1M / 5M индекс создавался, измерялся запрос, затем индекс удалялся, чтобы не искажать следующие загрузки. На 10 млн индекс создан отдельно: Bitmap Heap Scan, **0.306 ms**.

План на 5 млн **с индексом**:

```
Bitmap Heap Scan on events  (actual time=0.022..0.114 rows=42 loops=1)
  Recheck Cond: (user_id = 123)
  Heap Blocks: exact=42
  ->  Bitmap Index Scan on idx_events_user_id
        Index Cond: (user_id = 123)
Execution Time: 0.132 ms
```

| Объём | Без индекса | С индексом | Разница |
| ---: | ---: | ---: | ---: |
| 100 000 | 3.557 ms | 0.053 ms | ~67× |
| 1 000 000 | 16.980 ms | 0.067 ms | ~253× |
| 5 000 000 | 72.421 ms | 0.132 ms | ~548× |

### Вопросы

1. **Как изменился план запроса?**  
   Seq Scan / Parallel Seq Scan сменился на `Bitmap Index Scan` + `Bitmap Heap Scan`. Появилось условие `Index Cond: (user_id = 123)`. Таблица больше не читается целиком: из heap берутся только блоки с найденными TID.

2. **Как изменилось время выполнения?**  
   С 3.6 / 17 / 72 ms до долей миллисекунды. Время с индексом почти не зависит от размера таблицы (0.05–0.13 ms), потому что селективность постоянная: ~10–50 строк из миллионов.

3. **На каком объёме данных разница стала заметной?**  
   Уже на 100 000 (3.6 ms против 0.05 ms). С 1 млн разница становится практической: 17 ms vs 0.07 ms. На 5–10 млн Seq Scan — это 70–140 ms на один точечный запрос, то есть индекс здесь обязателен.

4. **Всегда ли индекс является оптимальным решением?**  
   Нет. Если запрос возвращает большую долю таблицы, PostgreSQL сам выберет Seq Scan: последовательное чтение дешевле, чем случайные обращения к heap по TID. Индекс также нужно поддерживать при `INSERT`/`UPDATE`/`DELETE`. На очень маленькой таблице (10k) Seq Scan и так занимает 0.3 ms — индекс почти ничего не даёт.

## Задание 6. Поиск по диапазону дат

Запрос (на 10 млн строк, без индекса по `created_at`):

```sql
EXPLAIN ANALYZE
SELECT * FROM lab02.events
WHERE created_at >= NOW() - INTERVAL '1 day';
```

**Без индекса** — Parallel Seq Scan, 27 371 строка, `Rows Removed by Filter: 3 324 210` на воркера, **Execution Time: 403.345 ms**.

После

```sql
CREATE INDEX idx_events_created_at ON lab02.events(created_at);
```

**С индексом:**

```
Bitmap Heap Scan on events  (actual time=5.906..66.858 rows=27368 loops=1)
  Recheck Cond: (created_at >= (now() - '1 day'::interval))
  Heap Blocks: exact=23412
  ->  Bitmap Index Scan on idx_events_created_at
        Index Cond: (created_at >= (now() - '1 day'::interval))
Execution Time: 67.674 ms
```

Индекс ускорил запрос с 403 ms до 68 ms (~6×), но 68 ms — это всё ещё заметно. Причина: 27k строк размазаны по **23 412 heap-блокам**. Индекс быстро находит TID, а потом почти случайно читает кучу.

Контрольный запрос по **365 дням** (почти вся таблица) с тем же индексом PostgreSQL выполнил **Parallel Seq Scan**, индекс не использовал: **573 ms**. Планировщик правильно решил, что читать индекс + heap дороже, чем просто пройти таблицу.

### Вопрос. Почему индекс может давать хороший результат для небольшого диапазона, но быть менее полезным, если запрос возвращает большую часть таблицы?

Индекс выгоден, когда он отсекает большую часть строк (высокая селективность). Диапазон в 1 день — это ~0.27% таблицы (27k из 10M): Bitmap Scan оправдан. Диапазон в 365 дней — почти 100% строк: сначала читается почти весь индекс, затем почти вся куча, плюс random I/O. Seq Scan читает таблицу один раз последовательно и оказывается дешевле. Поэтому «индекс по дате» не универсален: он помогает узкому окну и перестаёт помогать, когда окно охватывает большую долю данных.

## Задание 7. Фильтрация и сортировка

```sql
EXPLAIN ANALYZE
SELECT * FROM lab02.events
WHERE user_id = 123
ORDER BY created_at DESC
LIMIT 100;
```

**Без дополнительных индексов** (10 млн строк):

```
Limit
  ->  Gather Merge
        ->  Sort  (Sort Key: created_at DESC)
              ->  Parallel Seq Scan on events
                    Filter: (user_id = 123)
                    Rows Removed by Filter: 3333303
Execution Time: 137.057 ms
```

Операция `Sort` есть. Сначала читается вся таблица, затем 92 найденные строки сортируются, затем `Limit`.

**После `idx_events_user_id`:** Bitmap Heap Scan (92 строки) + `Sort` + `Limit`, **0.101 ms**. `Sort` остался, но сортируются только 92 строки в 32 kB памяти — это дёшево.

**После составного индекса:**

```sql
CREATE INDEX idx_events_user_created ON lab02.events(user_id, created_at DESC);
```

Планировщик по-прежнему выбрал Bitmap Index Scan по `idx_events_user_created` + `Sort` (**0.264 ms**). `Sort` не исчез: подходящих строк всего 92, а `LIMIT 100` больше этого числа, поэтому сортировка крошечного набора дешевле, чем упорядоченный Index Scan.

Если запретить bitmap (`SET enable_bitmapscan TO off`), план становится таким:

```
Limit
  ->  Index Scan using idx_events_user_created on events
        Index Cond: (user_id = 123)
Execution Time: 0.523 ms
```

`Sort` исчезает: B-tree уже хранит строки с одним `user_id` в порядке `created_at DESC`, и Index Scan читает их в нужном порядке.

### Ответы

1. **Изменился ли план?** Да. Seq Scan сменился на индексный доступ (`idx_events_user_id`, затем `idx_events_user_created`).
2. **Исчезла ли операция Sort?** В естественном плане — нет, потому что совпадений мало и Bitmap+Sort дешевле. При Index Scan по составному индексу — да.
3. **Почему порядок колонок в индексе имеет значение?**  
   B-tree сортирует ключи слева направо. Индекс `(user_id, created_at DESC)` сначала группирует по пользователю, внутри группы — по дате. Его можно использовать для `WHERE user_id = $1` (левый префикс) и для `ORDER BY created_at DESC` внутри этого пользователя. Индекс `(created_at, user_id)` для равенства по `user_id` по правилу левого префикса не подходит.

## Задание 8. Агрегация

```sql
EXPLAIN ANALYZE
SELECT event_type, COUNT(*)
FROM lab02.events
WHERE created_at >= NOW() - INTERVAL '30 days'
GROUP BY event_type;
```

На 10 млн строк, индекс `idx_events_created_at` уже существует. В окно 30 дней попало **823 365** строк (~8% таблицы).

```
Finalize GroupAggregate
  Group Key: event_type
  ->  Gather Merge
        ->  Sort
              ->  Partial HashAggregate
                    Group Key: event_type
                    ->  Parallel Bitmap Heap Scan on events
                          Recheck Cond: (created_at >= (now() - '30 days'::interval))
                          Rows Removed by Index Recheck: 1213492
                          Heap Blocks: exact=17774 lossy=11788
                          ->  Bitmap Index Scan on idx_events_created_at
                                Index Cond: (created_at >= ...)
Execution Time: 365.220 ms
```

### Ответы

1. **Какие операции выполняются в плане?**  
   Bitmap Index Scan → Parallel Bitmap Heap Scan → Partial HashAggregate → Sort → Gather Merge → Finalize GroupAggregate.

2. **Какой объём данных необходимо обработать?**  
   ~823k строк, плюс lossy-перечитывание heap-блоков (`work_mem` не хватило на точный bitmap: 11 788 lossy-блоков). Это уже не точечный поиск.

3. **Помогает ли индекс на `created_at`?**  
   Да, он ограничивает чтение окном 30 дней вместо всей таблицы. Без него был бы Parallel Seq Scan на 10 млн строк. Но 365 ms — всё ещё дорого для интерактивного запроса.

4. **Может ли индекс полностью решить проблему производительности данного запроса?**  
   Нет. После фильтрации всё равно нужно прочитать сотни тысяч строк и агрегировать их. Покрывающий индекс `(created_at, event_type)` дал бы Index Only Scan, но не убрал бы объём агрегации. Для роста дальше нужны другие средства: материализованное представление, предварительная агрегация, партиционирование по времени, отдельное OLAP-хранилище.

## Задание 9. Стоимость индексов

Сравнение массовой вставки 100 000 строк в таблицу из 10 млн (`BEGIN` + `EXPLAIN ANALYZE INSERT` + `ROLLBACK`, данные не оставались).

| Состояние | Execution Time |
| :--- | ---: |
| Только `events_pkey` | **166.645 ms** |
| + `idx_events_user_id` + `idx_events_created_at` + `idx_events_user_created` | **2005.992 ms** |

Запись замедлилась примерно в **12 раз**.

### Вопросы

1. **Как изменилось время INSERT?** Выросло с 167 ms до 2006 ms.
2. **Почему наличие индексов может замедлять операции записи?**  
   Каждая новая строка — это не только запись в heap, но и вставка ключа в каждый B-tree: поиск листа, возможный split страницы, запись WAL по каждому индексу.
3. **Что происходит с индексами при добавлении новых строк?**  
   Для каждого индекса PostgreSQL находит место в B-tree, вставляет пару (ключ, TID). Если страница переполнена — она делится. Индексы сразу содержат новые строки; отдельный «пересчёт индекса» не нужен, но каждая вставка становится дороже.

**Вывод. Почему нельзя просто создать индекс на каждой колонке?**  
Индексы ускоряют выбранные `SELECT`, но линейно удорожают `INSERT`/`UPDATE`/`DELETE`, занимают диск (на 10 млн три вторичных индекса — сотни мегабайт) и могут запутать планировщик. Нужны только те индексы, которые закрывают реальные запросы.

## Задание 10. Исследование размера индексов

```sql

```

| Индекс | Размер |
| :--- | ---: |

### Вопрос. Как изменяется размер индекса при росте количества записей?

Размер B-tree растёт примерно линейно с числом строк. Составной индекс крупнее одноколоночного: в ключе больше байт (`user_id` + `created_at` против одного `user_id`). Индекс по `created_at` (8 байт timestamp, высокая кардинальность) заметно больше индекса по `user_id` (значения повторяются, страницы плотнее).

## Задание 11. Когда индекс уже не спасает?

Запрос:

```sql
SELECT DATE(created_at), COUNT(*)
FROM events
WHERE created_at >= NOW() - INTERVAL '365 days'
GROUP BY DATE(created_at);
```

Предположение: 100 миллионов записей, индекс по `created_at` есть.

1. **Почему запрос всё равно может быть дорогим?**  
   Условие `365 days` при данных за год почти не фильтрует: в работу идёт вся таблица (или почти вся). Затем к каждой строке применяется `DATE(created_at)` — это выражение, обычный индекс по `created_at` его не «закрывает». Нужна группировка по ~365 ключам на всём объёме.

2. **Какой объём данных необходимо обработать?**  
   При равномерном потоке за год — порядка **100 млн строк**. Даже Index Scan по `created_at` пройдёт практически все листья индекса и почти всю кучу. На 10 млн у нас аналогичный фильтр уже выбрал Seq Scan и занял 573 ms только на `count(*)` без `GROUP BY DATE(...)`. На 100 млн это секунды или десятки секунд.

3. **Почему наличие индекса не гарантирует мгновенное выполнение запроса?**  
   Индекс ускоряет поиск **небольшой** доли строк. Если нужно прочитать и преобразовать почти все строки, узкое место — объём данных, а не поиск. Плюс `GROUP BY DATE(created_at)` не может взять готовый порядок из B-tree по timestamp без выражения.

4. **Какие решения можно рассмотреть, если таблица продолжит расти?**  
   - Партиционирование по месяцу/дню: `WHERE created_at >= ...` отсечёт старые партиции (partition pruning).  
   - Материализованное представление с дневными счётчиками, обновляемое по крону или триггером.  
   - Индекс по выражению `DATE(created_at)` или отдельная колонка `event_date`.  

Это совпадает с измерениями части A: индекс хорошо сработал для `user_id = 123` (десятки строк) и заметно хуже для окна 30 дней (823k строк) и бесполезен для окна 365 дней.

```sql
    bookings.id, bookings.user_id, bookings.book_id, bookings.status,
    bookings.created_at, bookings.returned_at, books.title AS book_title
FROM bookings
JOIN books ON bookings.book_id = books.id
WHERE bookings.user_id = 1
ORDER BY bookings.created_at DESC
LIMIT 20 OFFSET 0;
```

```
  Sort Key: created_at DESC
  Sort Method: external merge  Disk: 19064kB
  ->  Bitmap Heap Scan on bookings  (actual time=26.198..136.400 rows=410730)
```

## Задание 18. Попробуйте улучшить запрос

Проблема запроса 2 — объём результата, а не отсутствие индекса (`ix_bookings_created_at` уже есть). Увеличение `work_mem` до 64 MB убрало disk sort (quicksort, 43 MB), но время осталось **328 ms**: узкое место — heap, не сортировка.

Рабочий приём в API — пагинация, как уже сделано в `get_all_bookings`:

```sql
SELECT id, user_id, book_id, status, created_at, returned_at
FROM bookings
WHERE created_at BETWEEN NOW() - INTERVAL '30 days' AND NOW()
ORDER BY created_at DESC
LIMIT 20;
```

План после изменения:

```
Limit  (actual time=0.014..0.083 rows=20 loops=1)
  ->  Index Scan Backward using ix_bookings_created_at on bookings
        Index Cond: ((created_at >= ...) AND (created_at <= now()))
Execution Time: 0.125 ms
```

| Вариант | Время на 5M | Что изменилось |
| :--- | ---: | :--- |
| Исходный SELECT без LIMIT | 277 ms | 411k строк, disk sort |
| `work_mem = 64MB` | 329 ms | Sort в памяти, heap тот же |
| `LIMIT 20` | **0.125 ms** | Index Scan останавливается после 20 строк |

Время упало примерно в **2200 раз**. Семантика API при этом становится честной: список на экране не должен выгружать сотни тысяч строк.

Дополнительно для запроса 3 (он тоже деградировал из-за неверного индекса) создан составной индекс под паттерн «история читателя»:

```sql
CREATE INDEX idx_bookings_user_created
ON bookings(user_id, created_at DESC);
```

После этого:

```
Limit
  ->  Nested Loop
        ->  Index Scan using idx_bookings_user_created on bookings
              Index Cond: (user_id = 1)
        ->  Index Scan using ix_books_id on books
Execution Time: 0.138 ms
```

`Sort` исчез, Filter по `user_id` исчез, время с 25.5 ms до 0.14 ms. Это правильный индекс для `GET /api/users/{id}/bookings`. Одиночные `ix_bookings_user_id` и `ix_bookings_created_at` этот сценарий на большом объёме закрывают хуже.

Итог улучшения: для выгрузки за период одного индекса мало — нужно ограничивать объём (LIMIT/курсор, отчёт, партиция). Для ленты пользователя — нужен составной индекс, совпадающий с `WHERE` + `ORDER BY`.

## Задание 19. Граница применимости индексов

При объёме около **1 млн** бронирований запрос `get_bookings_in_range` за 30 дней начинает сортировать ~83 000 строк на диске и занимает **~43 ms**; индекс `ix_bookings_created_at` при этом используется. На **5 млн** тот же запрос обрабатывает **~411 000 строк**, читает 40 тысяч heap-блоков из-за корреляции `created_at ≈ 0.004` и занимает **~277 ms**. Добавление памяти под сортировку почти не помогло. `LIMIT 20` уменьшил время до **0.13 ms**, но это уже другой запрос: индекс снова работает как OLTP-доступ, а не как движок выгрузки.

Параллельно точечный `WHERE user_id = 123` на экспериментальной `events` с индексом остался в пределах **0.3 ms даже на 10 млн строк**, тогда как Seq Scan на том же объёме занял **137 ms**.

Поэтому граница такая:

- **Индекса достаточно**, пока запрос забирает небольшую селективную долю строк (поиск по `user_id`, страница ленты с `LIMIT`). Это устойчиво до миллионов и десятков миллионов строк.  
- **Индекса недостаточно**, когда результат — большой процент таблицы или полная агрегация. В этом сервисе это произошло уже при **~1 млн** броней для месячной выгрузки без LIMIT и стало явным на **5 млн** (сотни миллисекунд, диск, 8% таблицы). Дальнейший рост снова увеличит время примерно линейно. Здесь нужны пагинация, партиционирование, предрасчёт или отдельный контур аналитики — не «ещё один btree».

# Контрольные вопросы

1. **Почему Seq Scan не всегда является плохим планом?**  
   Последовательное чтение выгодно, если нужна большая доля таблицы, таблица маленькая или индекс привёл бы к почти полному random I/O по heap. На 10 млн событий фильтр «последний год» PostgreSQL сам выбрал Seq Scan (573 ms) вместо индекса.

2. **Почему PostgreSQL может не использовать существующий индекс?**  
   Низкая селективность, устаревшая статистика, несовпадение выражения (`DATE(created_at)` vs индекс по timestamp), дешевле Seq Scan, либо другой индекс кажется полезнее для `ORDER BY`/`LIMIT` (как `ix_bookings_created_at` вместо `ix_bookings_user_id` в запросе 3).

3. **Что происходит с индексом при INSERT?**  
   В каждый B-tree вставляется ключ новой строки и TID. При переполнении страницы — split. WAL пишется и для таблицы, и для индексов.

4. **Почему большое количество индексов может замедлять запись?**  
   Стоимость вставки умножается на число индексов. 100k `INSERT` в `events`: 167 ms с одним PK против 2006 ms с тремя вторичными индексами.

5. **Что такое селективность?**  
   Доля строк, удовлетворяющих условию. Высокая селективность (мало строк) — индекс полезен. `user_id = 123` на 10 млн — ~0.001%. Окно 365 дней — ~100%.

6. **Почему индекс хорошо работает для поиска небольшой части таблицы?**  
   B-tree находит TID за O(log N), из heap читаются только нужные страницы. На 5 млн `user_id = 123` — 0.13 ms вместо 72 ms.

7. **Почему индекс может быть менее полезен, если запрос возвращает большую часть таблицы?**  
   Нужно прочитать почти весь индекс и почти всю кучу случайным образом. Seq Scan один раз проходит heap последовательно и оказывается дешевле.

8. **Зачем нужен EXPLAIN ANALYZE?**  
   Он **выполняет** запрос и показывает фактические время, строки, буферы, методы сортировки. Обычный EXPLAIN — только оценка планировщика.

9. **Что означает Rows Removed by Filter?**  
   Сколько строк узел прочитал и отбросил, потому что условие не попало в Index Cond и проверялось как Filter. Большое значение — работа впустую (Seq Scan без индекса или неверный индекс + пост-фильтр).

10. **Что означает Index Cond?**  
    Условие, которое индекс смог применить сам, без чтения лишних строк таблицы.

11. **Чем Index Scan отличается от Bitmap Index Scan?**  
    Index Scan идёт по листьям B-tree и сразу достаёт heap-строки (может сохранить порядок индекса). Bitmap Index Scan собирает битовую карту TID, сортирует их по страницам и читает heap пакетами — выгоднее, когда совпадений много и порядок не нужен.

12. **Почему порядок колонок в составном индексе имеет значение?**  
    Правило левого префикса: индекс `(user_id, created_at DESC)` обслуживает фильтр по `user_id` и сортировку по дате внутри пользователя. Перестановка колонок — это другой индекс.

13. **Почему запрос с GROUP BY может оставаться дорогим даже при наличии индекса?**  
    Индекс может сузить диапазон, но агрегировать всё равно нужно все прошедшие фильтр строки. На 10 млн событий GROUP BY за 30 дней — 823k строк и 365 ms.

14. **Как статистика влияет на выбор плана?**  
    `ANALYZE` оценивает ndistinct, MCVs, гистограммы, корреляцию. От этого зависят estimated rows и выбор Seq/Index/Bitmap. Без актуальной статистики планировщик ошибается в селективности.

15. **Что происходит с производительностью при росте таблицы?**  
    Seq Scan и агрегации без ограничения объёма деградируют линейно. Селективные индексные запросы с LIMIT остаются стабильными. Планировщик может сменить план (как запрос 3 на 1 млн).

16. **Почему нельзя создавать индексы на все колонки?**  
    Диск, замедление записи, дублирование, риск выбора неоптимального индекса. Нужны индексы под конкретные запросы.

17. **Как определить размер таблицы в PostgreSQL?**  
    `pg_size_pretty(pg_relation_size('table'))` — heap; `pg_total_relation_size('table')` — heap + TOAST + индексы.

18. **Как определить размер индекса?**  
    `pg_size_pretty(pg_relation_size('index_name'))` или выборка из `pg_stat_user_indexes` по `indexrelid`.
