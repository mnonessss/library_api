### Вопрос 1. Чем EXPLAIN отличается от EXPLAIN ANALYZE?
EXPLAIN только показывает предполагаемый план на основании статистики, а EXPLAIN ANALYZE реально выполняет запрос и выводит не только стратегию выполнения этого запроса, но и фактические метрики.

### Вопрос 2. Почему EXPLAIN ANALYZE может выполняться значительно дольше, чем EXPLAIN?
Потому что EXPLAIN ANALYZE реально выполняет запрос и работает с данными, а EXPLAIN только строит план выполнения запроса, основываясь на статистике, это очень быстрая операция, в отличие от реальной работы с данными.

### Вопрос 3. Чем отличаются предполагаемые (estimated) и фактические (actual) значения количества строк?
Estimated rows - это количество строк, которое предсказал планировщик на основе статистики, а actual rows - это реальное количество строк, полученных при фактическом выполнении.

## Задание 10. Bitmap Index Scan

![](image-10.png)

![](image-11.png)

### Вопрос 1. Что делает Bitmap Index Scan?
Bitmap Index Scan читает Index и создает bitmap, в которрой каждый бит отвечает за блок таблицы (1 = в блоке есть подходящие записи, 0 - в блоке таких записей нет)

### Вопрос 2. Что делает Bitmap Heap Scan?
Bitmap Heap Scan получает от Bitmap Index Scan bitmap, читает только те блоки таблицы, для которых в bitmap стоит единица, внутри каждого блока проверяет строки и возвращает подходящие по условию строки

### Вопрос 3. Почему PostgreSQL может использовать Bitmap Scan вместо обычного Index Scan?
PostgreSQL может так сделать, если нужно вернуть не слишком мало, но и не слишком много записей, т.к. при Bitmap Scan сначал будет создана bitmap за счет обращения к индексу, а потом пакетное чтение - это быстрее чем случайные четния, которые получаются при использовании Index Scan.

### Вопрос 3. От чего зависит выбор между несколькими индексами и одним составным?

PostgreSQL использует правило левого префикса, т.е. составной индекс может использоваться только если запрос содержит условия по левой колонке индекса или по нескольким колонкам слева направо без пропусков

### Вопрос 2. Почему (user_id, created_at) и (created_at, user_id) — это разные индексы?
Порядок перечисления полей определяет структуру B-Tree, используемого в качестве индекса. Сортировка будет идти от левого поля к правому, т.е. в первом случае БД будет сначала сортировать по user_id, а уже потом, внутри групп с одинаковым user_id, будет сортировать по created_at, а во втором случае все происходит с точностью до наоборот.

### Вопрос 1. Чем Index Only Scan отличается от обычного Index Scan?
Index Only Scan ищет записи только в индексе, т.е. если поля нет в индексе - он не пойдет за ним в таблицу. Index Scan сначала идет в индекс, там находит TID нужной записи и по этому адресу идет в таблицу и оттуда забирает нужные записи.

### Вопрос 2. Почему PostgreSQL может не обращаться к основной таблице?
Потому что все нужные данные уже есть в нашем индексе (и id, и user_id)

### Вопрос 3. Какие условия необходимы для выполнения Index Only Scan?
Все переменные, встречающиеся в WHERE, ORDER BY, GROUP BY, SELECT должны быть в индексе (или INCLUDE). Также статистика должна быть актуальна

### Дополнительное задание
Индекс с INCLUDE добавляет колонки id, status и created_at как «полезную нагрузку» — они хранятся в индексе, но не участвуют в поиске и сортировке. Это позволяет выполнять Index Only Scan (не обращаться к таблице) для запросов с WHERE user_id = значение, что ускоряет выполнение и снижает нагрузку на диск. Однако такой индекс не может использоваться для поиска или сортировки по included-колонкам — для этого нужен составной индекс с этими колонками в ключе. INCLUDE даёт меньший размер индекса и быстрее обновляется по сравнению с составным индексом.

## Задание 22. Выберите Scaling Entity

1. **Название таблицы:** `bookings`.

2. **За что отвечает данная сущность.**
Таблица хранит факты бронирования книг читателями. Одна строка — одно обращение читателя за книгой: кто взял (`user_id`), какую книгу (`book_id`), в каком статусе сейчас находится выдача (`ACTIVE` / `RETURNED` / `OVERDUE`), когда бронь создана (`created_at`) и когда книгу вернули (`returned_at`).

3. **Почему именно эта таблица будет расти быстрее остальных.**
Пользователи, книги и категории — относительно стабильные справочники. Новая строка в `bookings` появляется при каждом визите читателя в библиотеку, то есть это журнал событий, а не справочник. Даже если каталог книг почти не меняется, бронирования копятся линейно с числом читателей и их активностью. Отзывы (`reviews`) тоже растут, но не каждый читатель оставляет отзыв на каждую взятую книгу, поэтому `bookings` обгоняет остальные таблицы.

4. **Какой потенциальный объём данных вы ожидаете через год.**
Предположим, в год в среднем на одного человека будет около 50 выдач, в библиотеку скорее всего придут новые читатели, поэтому через год в таблице `bookings` будет порядка 200000 записей.

- `status` стоит первым — это равенство, без левого префикса диапазон по дате не попадёт в индекс;
- `created_at` стоит вторым — диапазон и потенциальная сортировка `ORDER BY created_at`.

```sql
CREATE INDEX idx_bookings_status_created_at
ON bookings (status, created_at);
```

По правилу левого префикса этот индекс обслужит и запросы только по `status`, и запросы `status + created_at`, и `ORDER BY created_at` внутри одного статуса (сканирование вперёд или назад).

# Часть 23. Финальный вопрос

## Задание 30. Почему нельзя индексировать всё?

Индекс — это не бесплатное ускорение `SELECT`, а отдельная физическая структура. Её нужно хранить на диске и поддерживать согласованной с таблицей при каждой записи. Поэтому индексировать «все колонки на всякий случай» нельзя: выигрыш на чтении почти всегда оплачивается объёмом и замедлением записи.

**Размер индексов.**
B-tree хранит копию ключей и ссылки на строки таблицы (TID). Чем больше колонок проиндексировано — и тем более чем больше составных индексов на комбинации колонок, — тем больше индексный слой. На широкой таблице индексы легко становятся сравнимы с самой таблицей или превосходят её.

**Стоимость хранения.**
Лишние индексы занимают диск, место в shared buffers и попадают в бэкапы и реплики. Растёт не только объём данных, но и стоимость их хранения и передачи.

**INSERT.**
При вставке строки СУБД записывает её в таблицу и затем вставляет ключ в каждый индекс: нужно найти место в B-tree, при переполнении страницы — разделить её. Чем больше индексов, тем дороже каждая вставка. Это уже было видно в задании 19: после появления индексов `INSERT` замедлился.

**UPDATE.**
Индекс нужно обновлять, если изменилась проиндексированная колонка. Чем больше индексов затрагивают изменяемые поля, тем дороже типичный `UPDATE`.

**DELETE.**
Удаление строки требует удаления соответствующей записи из каждого индекса. Мёртвые ключи потом убирает `VACUUM`. Лишние индексы увеличивают работу autovacuum.

**Необходимость обновления индексов.**
Как было сказано выше, при INSERT/UPDATE/DELETE необходимо изменить не только саму таблицу, но и индекс - где-то перезаписать TID, где-то полезную нагрузку, где-то поделить страницу B-Tree, если страница переполнена

**Влияние на скорость записи.**
Нагрузка на запись идёт постоянно. Ускорение редкого `SELECT` может быть полностью съедено замедлением каждого `INSERT`/`UPDATE`/`DELETE`. Индекс оправдан, только если его достаточно часто читают, чтобы окупить стоимость поддержки.

**Реальное использование запросами.**
Планировщик берёт индекс, только если он подходит по колонкам, порядку (правило левого префикса), селективности и стоимости. Индекс по низкоселективной колонке, индекс, который не совпадает с условием запроса, или индекс, дублирующий уже существующий, может вообще не использоваться. Такой индекс не ускоряет чтение, но продолжает занимать место и тормозить запись. Поэтому индексы создают под конкретные запросы, проверяют их `EXPLAIN ANALYZE` и статистикой `idx_scan` и не держат «на все колонки» без измерения.
