# Лабораторная 6. Что происходит с backend после шардирования


## 1. Архитектура

```text
Backend  (FastAPI)
    │
    │  app/sharding/router.py
    │  get_db_for_user(user_id)  →  ShardRouter
    │  modulo: MD5(id) % N
    │  consistent: точка на ring → ближайший shard
    ▼
 Router
    │
    ├── postgres-shard-0   users
    ├── postgres-shard-1   users
    └── postgres-shard-2   users

bookings, reviews, books / categories — postgres-primary (+ replica)
```

Router знает shard только если в запросе есть shard key. Нет `user_id` — backend опрашивает все три PostgreSQL (scatter-gather).

Как именно считается номер — две стратегии из лабы 5 (`SHARD_STRATEGY`). **Не одна и та же формула.** `hash % N` даёт индекс 0…N−1. Consistent Hash кладёт `MD5(id)` на кольцо и идёт по часовой до ближайшей точки шарда (vnode). Для одного ключа оба способа возвращают **ровно один** PostgreSQL — поэтому single-shard / JOIN / COUNT / LIMIT в этой лабе от стратегии не зависят. Меняется только кто владеет ключом при росте N.

В работающем compose стоит `SHARD_STRATEGY=modulo`: 100 000 профилей вставляли через `hash % 3`, `GET /api/users/101` идёт на shard 1. Кольцо в коде есть (`ConsistentHashRing`), но данные лежат по modulo; включать `consistent` без переноса строк нельзя — 101 мог бы оказаться на другом узле.

## 2. Single-Shard Query

Запрос сервиса:

```sql
SELECT id, name, email, created_at
FROM users
WHERE id = :user_id;
```

Endpoint: `GET /api/users/{user_id}`. Сессия открывается через `Depends(get_db_for_user)`: `ShardRouter` по ключу выбирает **один** экземпляр (сейчас modulo: `MD5(user_id) % 3`). Пример из лабы 5: пользователь `101` живёт на `postgres-shard-1` и ни на 0, ни на 2 его строки нет.

Почему другие шарды не нужны: строка с первичным ключом `id = 101` создана на том shard, который вернул router в момент `INSERT`. Повторный `SELECT` с тем же ключом попадает туда же. На shard 0 и shard 2 этой строки нет — опрашивать их бессмысленно.

## 3. Агрегирующий запрос

Агрегат по шардированной таблице есть в эндпоинте `GET /api/users/count`:

```sql
SELECT COUNT(*) FROM users;
```

До шардирования его выполнял один PostgreSQL. Теперь профили на трёх шардах, полного `COUNT` ни в одной базе нет. `count_users()` шлёт этот SQL на shard 0, 1 и 2 и складывает.

После загрузки 100 000 читателей:

```text
Shard 0 → 33 241
Shard 1 → 33 570
Shard 2 → 33 189
        ↓  aggregation в backend
      100 000
```

Ответ клиенту: `{"count": 100000}`.

### Ответы

1. **Можно ли выполнить такой запрос только на одном shard?** Нет. Один shard знает только свой кусок: 33 241 ≠ 100 000. В запросе нет `user_id`, router не выбирает узел.

2. **Где должны объединяться результаты?** В backend (`app/sharding/users.py`, `count_users`). Три независимых `COUNT(*)`, сумма в приложении. PostgreSQL шардов друг друга не видит.

3. **Что происходит со временем выполнения при увеличении количества shard’ов?** Увеличивается количество шардов, которые нужно опросить. Больше узлов — нужно будет дольше ждать, т.к. ответ нельзя отдать, пока не ответил последний шард, т.е. один медленный шард будет держать весь эндпоинт.

## 4. JOIN между shard’ами

**JOIN** — кто брал книгу, `GET /api/books/{book_id}/bookings`:

```sql
SELECT bookings.*, users.name AS user_name
FROM bookings
JOIN users ON bookings.user_id = users.id
WHERE bookings.book_id = :book_id
ORDER BY bookings.created_at DESC;
```

Связанные данные на **разных** кластерах: факт выдачи на Primary, имя читателя на шарде, который вернул router для этого `user_id` (при modulo — `postgres-shard-{MD5(user_id) % 3}`).

```text
postgres-primary                         postgres-shard-1
bookings (user_id = 101, book_id = 5)    users (id = 101, name = …)
books
        └──── JOIN users.id ──── на Primary этой строки users уже нет
```


### Ответы

1. **Что произойдёт, если связанные записи на разных shard’ах (здесь — Primary и шарды users)?** SQL на Primary делает `JOIN users`, но актуальные профили не там. JOIN вернёт выдачи без имён или не найдёт строки. SQL на шарде пользователя не видит `bookings`. Один запрос не склеивает две базы.

2. **Можно ли выполнить такой JOIN обычным SQL к одному PostgreSQL?** Нет: нет общего каталога `bookings`+`users`. Нужен lookup в приложении: с Primary взять выдачи, по `user_id` сходить на шарды за именами.

3. **Какие данные пришлось бы передавать?** С Primary — строки `bookings` с этим `book_id`. С шардов — `users.name` по списку `user_id` (router на каждый id). Склейка в backend. Между пользовательскими шардами выдачи не ездят: их там нет.

4. **Можно ли выбрать shard key, чтобы JOIN чаще был внутри одного shard?** Если положить `bookings` на тот же `user_id`, имя и выдача читателя окажутся на одном PostgreSQL, но «все выдачи книги» всё равно размажутся по трём шардам. Ключ `book_id` локализовал бы карточку книги и сломал бы историю читателя. Поэтому смысла создавать другой shard key нет.

## 5. ORDER BY + LIMIT

Список читателей — `GET /api/users/?skip=0&limit=20`:

```sql
SELECT id, name, email, created_at
FROM users
ORDER BY id
LIMIT :limit OFFSET :skip;
```

Профили на трёх шардах. Это `list_users()`: каждый PostgreSQL отдаёт свой кусок, backend сливает.

```text
Shard 0 → 20 строк ORDER BY id
Shard 1 → 20 строк ORDER BY id
Shard 2 → 20 строк ORDER BY id
        ↓  merge в backend, снова ORDER BY id, LIMIT 20
      глобальные первые 20 id
```

Почему недостаточно взять 20 записей только с shard 0: наименьшие id библиотеки размазаны по всем трём узлам. На shard 1 может лежать `id = 2`, меньше любой строки, которую вернул shard 0 в своём локальном top-20. Локальный LIMIT 20 — лучшие id **этого** куска, не всего сервиса.

Поэтому с каждого шарда берут не меньше `limit` (для страницы со `skip` — `skip + limit`), сортируют вместе по `id` и отрезают срез. Так и сделано в `list_users()`.

Глубокий `OFFSET` плох так же: чтобы отдать страницу 500, с каждого шарда нужно привезти много строк. Для больших списков лучше cursor (`WHERE id > :last`), а не большой OFFSET.

## 6. Отказ одного shard

```text
Shard 0 ✓    Shard 1 ✓    Shard 2 ✗
```

Пусть недоступен `postgres-shard-2` (~33% пользователей, в эксперименте 33 189 профилей, в том числе id `103`, `50000`, `99999`).

1. **Какие данные недоступны?** Все `users`, которых router кладёт на shard 2 (при текущем modulo — `MD5(id) % 3 = 2`). Каталог книг на Primary жив. Читатели шардов 0 и 1 на месте.

2. **Какие endpoint’ы перестанут работать?**
   - `GET/PUT/DELETE /api/users/{id}` для id с шарда 2 — ошибка соединения;
   - `GET /api/users/{id}/bookings` и `/reviews` этих id;
   - `GET /api/users/`;
   - `POST /api/users` — `allocate_user_id()` делает `MAX(id)` по всем шардам, без шарда 2 новый id не выделить;
   - `GET /api/users/count` — не соберёт полный `COUNT` читателей;

3. **Остальная часть сервиса?** Каталог `GET /api/books`, популярные книги с Primary, профили шардов 0 и 1 — продолжат работать, т.к. в этих запросах не используется шард 2.

4. **Что делать backend при обращении к мёртвому shard?** Не ждать бесконечно: короткий timeout, ответ `503`. Для списка/агрегата — либо отказ всего запроса (строгая целостность), либо частичный результат с флагом `partial=true` (для админки допустимо, для «всего журнала выдач» — нет). Повторять запрос на соседний shard бессмысленно: строк там нет.

   Consistent Hashing сам данные не переносит. Если выкинуть shard 2 из кольца, ключи в **формуле router’а** начнут указывать на следующий узел по часовой. Сосед примет `GET /api/users/103`, но строки в его `users` нет — будет 404, не failover. Чтобы сосед отвечал, копии нужно было заранее класть на N следующих узлов кольца (Dynamo) либо поднять replica **этого же** шарда. У нас ring только выбирает PostgreSQL.

5. **Отказоустойчивость.** У каждого шарда своя replica (как в лабе 4). При падении master шарда 2 router идёт на replica шарда 2, кольцо не перестраивают. Бэкап и restore — пошардово. Отказ шарда 2 без replica — потеря его ключей.

## 7. Hot Shard

```text
Shard 0 → 10% запросов
Shard 1 → 15% запросов
Shard 2 → 75% запросов
```

Возможные причины:

- **Неудачный ключ.** Шард по первой букве фамилии:какие-то буквы могут собрать сильно больше остальных
- **Неравномерные данные.** Если шардировать `bookings` по `book_id`, бестселлер осядет на одном PostgreSQL.
- **Популярный пользователь.** Читатель с id на shard 2 берёт книги каждый час — тысячи `GET /api/users/2/bookings` и `POST /api/bookings`. Соседи простаивают.
- **Тип запросов.** Админ чаще смотрит журнал (`GET /api/bookings` — все шарды). Читатели бьют в профиль — hot key. `GET /api/books/popular` всегда трогает все три, hot shard по CPU будет тот, где больше выдач, не тот, где больше строк `users`.

**Почему равное число строк ≠ равная нагрузка?** К одним шардам могут обращаться очень часто, а к дргуи наоборот очень редко. Например, если шардирование идет по месяцам, то к шарду текущего месяца обращаться будут очень часто, а к другим - гораздо реже.

## 8. Итоговый анализ shard key

Ключ: **`users.id` / `user_id`**.

### Плюсы

Эффективны запросы «про одного читателя»:

- профиль `GET/PUT/DELETE /api/users/{id}`;
- история `GET /api/users/{id}/bookings` и `/reviews`;
- создание выдачи и отзыва, если в теле есть `user_id`.

Router открывает один PostgreSQL. Это основной трафик личного кабинета.

### Минусы

Становятся распределенными:

- список всех читателей `GET /api/users/`;
- журнал всех выдач `GET /api/bookings` без `user_id`;
- карточка книги `GET /api/books/{id}/bookings` и `/reviews`;
- `GET /api/books/popular` (`COUNT` + `GROUP BY`);
- `GET /api/reviews/stats/ratings` (`AVG` + `GROUP BY`);
- `GET /api/bookings/{id}` и `GET /api/reviews/{id}`


### Проблемные операции

| Операция | Насколько сложно |
| :--- | :--- |
| JOIN `bookings` × `books` (история читателя) | локальный: обе таблицы на Primary |
| JOIN `bookings` × `users` (кто брал книгу) | сломан обычным SQL: users на шардах, bookings на Primary |
| aggregation (`COUNT`, `AVG`, `GROUP BY` по книге) | только через merge в backend |
| `ORDER BY … LIMIT` глобальный список | merge top-K со всех шардов |
| migration 3 → 4 | modulo гоняет ~75% ключей (лаба 5); consistent hashing ~28% |
| backup | три независимых дампа, нельзя одним `pg_dump` с Primary |
| восстановление | restore одного шарда не поднимает другие шарды, их нужно восстанавливать по отдельности |
| балансировка | строки на шардах распределены примерно  поравну |

### Вывод

Ключ **оставил бы**. Библиотека в первую очередь отвечает «что у этого читателя»: профиль, история, новая выдача. Это single-shard при `user_id`. Ключ `book_id` ускорил бы топ книг и карточку издания, но размазал бы кабинет читателя — его дергают чаще. Каталог не шардировать. Глобальные отчёты (`popular`, средний рейтинг, журнал библиотекаря) заранее считать scatter-gather или вынести на отдельную витрину. Для роста числа PostgreSQL — consistent hashing с virtual nodes, не `hash % N`.

## Вопросы для самопроверки

1. **Single-shard vs distributed.** Single-shard: router по ключу открывает один PostgreSQL (`GET /api/users/101`). Distributed: ключа нет или он не покрывает все нужные строки — опрос нескольких экземпляров и merge в приложении (`GET /api/users/`, `popular`).

2. **Почему JOIN между шардами сложнее обычного JOIN** Нет общей БД и общего планировщика. `JOIN users ON …` в `GET /api/books/{id}/bookings` не видит профили на шардах. Нужны два запроса и склейка

3. **COUNT(*) по всем шардам.** `SELECT COUNT(*) FROM users` на каждом шарде, сложить в backend. Так устроен `GET /api/users/count`: 33241+33570+33189 = 100000.

4. **Почему ORDER BY LIMIT требует merge.** Локальный top-N — лучшие строки **этого** куска. Глобальные лучшие могут лежать на любом шарде. Берут top-N с каждого, сортируют вместе, оставляют N.

5. **Отказ одного шарда.** Пропадают ключи этого узла (~⅓ профилей). Запросы к этому шарда — ошибка. Каталог и другие шарды живы. Без replica данные шарда 2 негде взять.

6. **Что такое Hot shard.** Узел, который обслуживает непропорционально много запросов или I/O, даже если строк столько же, сколько у соседей.

7. **Почему выбор shard key влияет на JOIN.** От того, как будут порезаны на шарды данные, зависит, можно ли будет применить JOIN к таблице. Например, нельзя напрямую средствами SQL сделать JOIN двух шардов

8. **Какие операции особенно плохо подходят для распределённых данных?** Те, которым нужна сразу вся таблица или две таблицы в одной транзакции PostgreSQL. В нашем сервисе это глобальный `COUNT`/`GROUP BY` (`GET /api/users/count`, топ книг если бы шардировали `bookings`), `JOIN bookings × users` (`GET /api/books/{id}/bookings`), `ORDER BY id LIMIT` по всем читателям, уникальный `email` на кластере, глубокий `OFFSET`, атомарное «списать экземпляр книги + записать выдачу», если книга и читатель на разных узлах. Single-shard `GET /api/users/{id}` к этому списку не относится.

9. **Что произойдёт при изменении количества shard’ов?** Router начнёт считать владельца ключа заново. При `hash % N` почти все ключи меняют узел (лаба 5, 3→4: 74.95%). Consistent Hashing двигает только дугу нового (или удалённого) шарда, ~28% при 3→4.

10. **Чем шардирование отличается от репликации?** Репликация — копии одной базы: Primary пишет, Replica читает то же самое; отказ replica данные не теряет. Шардирование — разные строки на разных PostgreSQL: shard 0 не содержит пользователей shard 2. Отказ шарда без своей replica — потеря его ключей. Реплика шарда 2 — это копия шарда 2

11. **Может ли шардирование сделать отдельный SQL-запрос быстрее?** Да, если запрос single-shard: `GET /api/users/101` сканирует ~33k строк на одном узле вместо 100k на одной машине. Нет, если запрос distributed: `GET /api/users/count` и `GET /api/users/` ждут все шарды и сливают результат — три сети + merge вместо одного плана. `GET /api/books/popular` сейчас на Primary шардированием users не ускоряется; если разрезать `bookings`, он скорее замедлится.
