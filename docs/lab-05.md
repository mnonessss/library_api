# Лабораторная 5. Шардирование PostgreSQL: Router и Consistent Hashing


## 1. Выбор данных для шардирования

### Какую сущность выбрали?

**Пользователи библиотеки** (`users`). Это корневая сущность сервиса: у пользователя есть бронирования и отзывы, профиль читается по `GET /api/users/{user_id}`.

### Какое поле используется как shard key?

**`users.id`** (тот же ключ, что `user_id` в `bookings` и `reviews`).

### Почему выбран именно этот ключ?

- Он есть во всех запросах к профилю: `GET`/`PUT`/`DELETE /api/users/{user_id}`.
- Он известен в момент записи бронирования и отзыва (`POST /api/bookings`, `POST /api/reviews`).
- `id` не меняется, в отличие от `email` или имени: смена почты не должна переносить строку на другую ноду
- По этому ключу можно колоцировать бронирования и отзывы с пользователем: все данные одного читателя живут на одном экземпляре. Тогда `GET /api/users/{id}/bookings` не превращается в scatter-gather по всем шардам.


### Насколько равномерно он будет распределять данные?

Идентификаторы выдаются подряд (`1 … 100000`). Если брать модуль от их хеша, то распределение будет практически идеально равномерным.

Неравномерность появится не из-за ключа, а из-за активности: один читатель может сделать тысячи бронирований. Тогда hotspot будет на шарде этого `user_id`. Для самой таблицы `users` (одна строка на человека) распределение должно быть почти ровным.

### Какие запросы сервиса используют этот ключ?

| Запрос | Куда идёт запрос |
| :--- | :--- |
| `GET /api/users/{id}` | `postgres-shard-{MD5(id) % 3}` — один из `postgres-shard-0`, `postgres-shard-1`, `postgres-shard-2` |
| `PUT /api/users/{id}` | `postgres-shard-{MD5(id) % 3}` |
| `DELETE /api/users/{id}` | `postgres-shard-{MD5(id) % 3}` |
| `POST /api/users` | сначала `MAX(id)+1` по всем шардам, затем `INSERT` в `postgres-shard-{MD5(новый_id) % 3}` |
| `GET /api/users/{id}/bookings` | ключ `id`; JOIN с книгами сейчас на `postgres-primary`, не на шардах |
| `GET /api/users/{id}/reviews` | ключ `id`; чтение с `postgres-primary` |
| `POST /api/bookings` с `user_id` | ключ `user_id` в теле; `INSERT` бронирования сейчас в `postgres-primary` |
| список `GET /api/users/` | ключа нет: `SELECT` с `postgres-shard-0`, `postgres-shard-1` и `postgres-shard-2`, строки сливаются в приложении |

Router в backend: `app/sharding/router.py`. Сессию нужного PostgreSQL открывает `get_db_for_user` в `app/sharding/pool.py` (это не `database.py`: там только Primary и Replica). Проверка: `GET /api/admin/shards/lookup/{user_id}`.

## 3. Простой Router: `hash(key) % N`

```text
shard = MD5(shard_key) % N
```

`N = 3`. Реализация — `ModuloRouter`:

```python
def shard_for(self, key) -> int:
    return stable_hash(key) % self.n
```

`GET /api/users/{user_id}` больше не ходит на Primary/Replica. FastAPI-зависимость `get_db_for_user(user_id)` открывает сессию того экземпляра, который вернул router.

Примеры на тех же ключах, что в задании (наш `MD5`, не абстрактный `hash`):

| key | `MD5(key) % 3` |
| ---: | :--- |
| 101 | **Shard 1** |
| 102 | **Shard 0** |
| 103 | **Shard 2** |

Проверка через API после загрузки:

```text
GET /api/users/101          → 200, User 101
GET /api/admin/shards/lookup/101
  → {"user_id": 101, "strategy": "modulo", "shard_index": 1, "found": true}
```

Пользователь 101 лежит на PostgreSQL 1 и не находится на 0 и 2.

## 4. Распределение данных

Загружено **100 000** пользователей (`id = 1 … 100000`, email `user{id}@library.local`) скриптом `scripts/shard_experiment.py`. Каждая строка вставляется в shard, который вернул `hash(id) % 3`.

`COUNT(*)` на живых PostgreSQL:

| Shard | Записей |
| :--- | ---: |
| Shard 0 | 33 241 |
| Shard 1 | 33 570 |
| Shard 2 | 33 189 |
| **Всего** | **100 000** |

Идеал при равномерном хеше: ~33 333 на экземпляр. Факт: разница max−min = **381** строка (**0,38%** от 100 000).

**Вывод.** Данные распределились равномерно. Заметного дисбаланса нет: отклонение меньше процента, для трёх одинаковых машин это не проблема. Дисбаланс стал бы проблемой, если бы один shard держал, например, 70% строк (маленький `N` без хеша, плохой ключ вроде `city`, или один «тяжёлый» `user_id` при шардировании бронирований). Для `users.id` + `MD5` такого эффекта нет.

`GET /api/admin/shards/` вернул те же счётчики: 33241 / 33570 / 33189.

## 5. Что произойдёт при добавлении shard: 3 → 4, `hash % N`

Раньше: `hash(key) % 3`. Станет: `hash(key) % 4`. Для того же набора из 100 000 id:

```text
Всего записей:  100 000
Изменили shard:  74 953
Не изменили:     25 047
Перемещено:      74.95%
```

Почему так много? Остаток от деления **зависит от N целиком**. `h % 3 == h % 4` только когда `h ≡ 0, 1 или 2 (mod 12)` — 3 класса из 12, то есть **~25% остаются**, **~75% едут**. Новый PostgreSQL забирает не «свою четверть с пустого места», а ломает нумерацию всех старых шардов: ключ со Shard 0 может оказаться на 0, 1, 2 или 3.

## 6. Consistent Hashing

Упрощённый ring в `ConsistentHashRing`:

1. Каждый shard получает точку на кольце: `hash("shard-i#vnode")`.
2. Ключ тоже становится точкой: `hash(user_id)`.
3. Идём по кольцу вперёд (по часовой) до ближайшей точки shard — это владелец ключа.
4. Если ключ «правее» всех точек, срабатывает wrap-around на начало кольца (`bisect` + индекс 0).

Базовая версия: **1 точка на физический shard** (`virtual_nodes=1`). Рядом — кольцо с **128 virtual nodes** на экземпляр: те же shard’ы, но много точек, дуги короче и перемешаны.

```text
hash(shard_key)
        ↓
точка на hash ring
        ↓
ближайший shard по кольцу
```

Имена узлов стабильны (`shard-0`, `shard-1`, `shard-2`). Новый экземпляр — это новая точка `shard-3`, старые точки **не пересчитываются**. Поэтому большинство ключей по-прежнему упираются в тот же узел.

## 7. Сравнение стратегий (тот же 3 → 4)

Четвёртый PostgreSQL для этого задания не поднимался: перенос считался на тех же `id = 1 … 100000`, что уже лежат на трёх шардах. Скрипт `scripts/shard_experiment.py` для каждого id вызывает старую функцию (`% 3` или ring из трёх имён) и новую (`% 4` или ring с `shard-3`) и считает, у скольких ключей имя/номер шарда изменился. Это не `UPDATE` и не копирование строк между контейнерами, а сравнение двух отображений ключ → shard.

Распределение на 3 узлах (для modulo — `COUNT(*)` в живых БД; для Consistent Hashing — `Counter` по `ring.get_node(id)`):

| | Shard 0 | Shard 1 | Shard 2 |
| :--- | ---: | ---: | ---: |
| `hash % 3` (факт в БД) | 33 241 | 33 570 | 33 189 |
| Consistent Hashing, 1 vnode | 22 412 | 45 173 | 32 415 |
| Consistent Hashing, 128 vnodes | 30 141 | 36 223 | 33 636 |

Перенос при **3 → 4**:

| Стратегия | Перемещено |
| :--- | ---: |
| `hash(key) % N` | **74.95%** |
| Consistent Hashing (1 vnode) | **4.96%** |
| Consistent Hashing (128 vnodes) | **27.99%** |


### Почему результаты отличаются?

`hash % N` меняет формулу для **каждого** ключа. Consistent Hashing меняет владельца только у ключей, чья точка на кольце попала на дугу, которую перехватил новый узел (или которая принадлежала удалённому). Остальные по-прежнему упираются в те же точки `shard-0`/`shard-1`/`shard-2`.

Базовое кольцо (1 vnode) в этом прогоне перенесло всего 4.96%: новый `shard-3` сел на короткую дугу. Цена — кривое распределение (45 173 vs 22 412). Это и есть причина virtual nodes.

### Почему Consistent Hashing уменьшает объём перемещаемых данных?

Новый shard занимает ~`1/(N+1)` кольца, а не перенумеровывает все остатки. Теоретически при 3 → 4 нужно перенести около **25%** ключей. С 128 vnode получилось **27.99%** — близко к теории и в **~2.7 раза меньше**, чем 74.95% у modulo.

### Что будет, если добавить ещё один shard?

Ещё раз ~`1/N_new` ключей перенесется.

### Что будет, если удалить shard?

Ключи удалённого узла едут к следующему по часовой (его virtual nodes). Остальные остаются.

## 8. Итог

Shard — это отдельный экземпляр PostgreSQL со своим куском данных, а не реплика той же базы. Shard key — поле, по которому router всегда однозначно находит этот экземпляр; в Library API это `users.id`. Router сидит в backend и подменяет «одну сессию SQLAlchemy» на сессию нужного шарда, чтобы `GET /api/users/101` не опрашивал все три PostgreSQL. Стратегия `hash(key) % N` дешёвая и на 100 000 пользователей дала почти идеальные 33k/33k/33k, но `N` входит в формулу: переход 3 → 4 ломает размещение **74.95%** строк. Consistent Hashing кладёт ключ и узлы на кольцо и при росте кластера двигает только дугу нового узла. Для сервиса библиотеки я бы шардировал пользователей (и колоцировал их бронирования) **consistent hashing с virtual nodes**: читателей станет больше, PostgreSQL будут добавлять по одному, и гонять три четверти профилей на каждый новый сервер нельзя. Каталог книг при этом можно оставить общим (Primary/Replica), а modulo оставить разве что для статичного числа шардов, которое заранее никогда не вырастет.

## Вопросы для самопроверки

1. **Что такое shard?** Отдельный независимый PostgreSQL (или другой storage), на котором лежит **часть** строк, а не полная копия. В работе это `postgres-shard-0/1/2`.

2. **Что такое shard key?** Поле записи, из которого router вычисляет владельца. Здесь — `users.id`. Хороший ключ есть в горячих запросах, стабилен и достаточно кардинален.

3. **Почему нельзя просто случайно распределять записи между PostgreSQL?** Повторный `GET` того же `user_id` должен попасть туда же, куда ушёл `INSERT`. Случайный выбор потребует центрального индекса «id → shard» на каждый запрос и не даст колоцировать бронирования пользователя.

4. **Как работает `hash(key) % N`?** Хеш приводит ключ к числу, остаток от деления на число шардов даёт номер `0 … N-1`. Одинаковый ключ всегда даёт один shard, пока `N` не изменился.

5. **Почему изменение количества shard’ов — проблема?** Меняется `N`, меняются все остатки. При 3 → 4 переезжает ~75% данных, иначе router смотрит не в ту базу. Пока идёт перенос, часть запросов видит «пусто».

6. **Что такое Consistent Hash Ring?** Кольцо из хешей: на нём лежат точки шардов и точка ключа. Владелец — ближайший shard по направлению обхода. Добавление узла вставляет новые точки, не пересчитывая старые.

7. **Почему при добавлении shard’а не приходится переносить все данные?** Меняется только дуга, которую перехватил новый узел. Ключи, которые по часовой по-прежнему упираются в старые точки, остаются на месте. Масштаб переноса ~`1/N_new`, а не `(N_new-1)/N_new`.

8. **Что такое virtual nodes и зачем они нужны?** Несколько точек кольца на один физический PostgreSQL (`shard-0#0`, `shard-0#1`, …). Одна точка на узел даёт длинные случайные дуги: в эксперименте 22k / 45k / 32k и «везучий» перенос 4.96%. 128 vnode выравнивают нагрузку (30k / 36k / 34k) и делают долю переноса предсказуемой (~28% при 3 → 4).

9. **Может ли Consistent Hashing гарантировать идеальное распределение?** Нет. Это вероятностное выравнивание. Даже с vnode остаётся разброс (у нас 30 141 vs 36 223). Идеала нет, если ключи с разным «весом» (активный читатель vs разовый).

10. **Что будет, если один shard станет заметно более загруженным?** Запросы к нему начнут тормозить, хотя остальные простаивают. Лечение: больше virtual nodes на холодные узлы / меньше на горячий, вынести горячий диапазон на новый PostgreSQL, сменить ключ, если hotspot системный (например, шардировали по городу).
